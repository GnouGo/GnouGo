## Files boundary and attachment resolution

Extract the HTTP-independent part of `FileStorageService` into a small `GnOuGo.Files.Core` library with the Files metadata/storage implementation. `Files.Server` translates HTTP into authenticated application calls and renews authorized download access. The local Agent.Server composition root can call the library in process. Desktop already hosts Agent.Server. Put the workflow adapter beside the host's runtime composition initially. Flow.Core retains its provider-neutral interface and zero GnOuGo dependencies. Files.Core takes no dependency on workflow planning, Web types or provider adapters.

Proposed minimal service surface, expressed as signatures. The host constructs the trusted scope from the authenticated principal, tenant, owner kind and ID. A model, HTTP parameter or workflow input cannot construct that authority. Each operation accepts cancellation.

```text
Put(scope, stream, declaredMediaType, operationId) -> FileRef
Attach(sourceGrant, targetScope, fileId, operationId) -> Hold
Open(scope, fileId) -> verified readable stream and FileRef
Release(scope, fileId, operationId) -> released or already released

FileRef = opaque fileId, sha256, validated MIME, byteLength, optional width/height
Hold key = tenant, ownerKind, ownerId, fileId
Workflow image lookup = tenant, executionRunId, sha256 -> fileId
```

Use unique keys for repeated writes/holds. Reject a reused operation ID carrying different bytes or a different destination. A temporary upload initially has a staging grant scoped to the authenticated uploader/conversation and its expiry. The resolver accepts a host-selected upload ID or an authorized Files download URL. Parse the configured Files origin and route into a local ID, then check the actual principal, source grant, tenant, time and target permission. Treat other origins as unsupported in this resolver. A separately approved external import can create a new upload. Old uploads lacking trusted provenance require explicit authorized import or re-upload. Keep owner-held records outside the existing header-selected temporary list/download queries. New chat staging is encrypted from upload and associated with the host principal. A legacy header-only client can access its existing temporary contract during migration. It cannot enumerate durable records or promote a file. Access to a public output grants only its intended download access. Enforce the current vision limits at import and again before use (eight images, 4 MiB each, 8,192 pixels per dimension, 16,777,216 pixels per image). Bound staging reads even when the client omits a content length.

At chat submission, before the temporary grant expires, acquire a planning or run hold. Return the usual validated image reference for an image binding. General documents keep a typed file reference. A session awaiting a reviewer can own an image without a run. At execution creation, acquire a separate run hold before publishing an input checkpoint. In a saved agent that will be used repeatedly, pin static dependencies to the saved agent and approved artifact version at save time. A future run acquires from that version under its own authorization. Transfer includes the approved artifact hash and provenance only. Invocation confirmations and execution permissions still come from existing approval paths. A user-kept deliverable acquires a distinct durable hold before the run can release its own.

`FilesWorkflowImageStore.PutAsync` verifies the supplied digest, persists the content and the tenant/run alias. `GetAsync` resolves that alias only inside the authorized run, authenticates the bytes and returns the existing byte array. Preserve the exact workflow reference fields `sha256`, `mimeType`, `width`, `height`, `size`. Adding `fileId` or an access URL to it would break the current exact JSON comparison. Keep those in Files metadata. Derive the adapter write identity from the trusted owner and digest. If concurrent writes stage the same image, commit one alias and collect the losing staging generation through its intent. Existing mixed MCP blocks, `images` bindings, agent observations, provider image parts, vision admission and receipts follow the same route. [Image reference validation](../src/GnOuGo.Flow.Core/Runtime/WorkflowImages.cs) · [MCP binding](../src/GnOuGo.Flow.Core/Runtime/Executors/McpCallExecutor.cs) · [Model binding](../src/GnOuGo.Flow.Core/Runtime/Executors/LlmCallExecutor.cs)

Encrypt durable contents before their first disk write, including staging files. Use application-managed authenticated encryption with a fresh data key per blob. Store its protected key material through the local GnOuGo KeyVault public API. Persist algorithm/envelope version, key reference, authenticated tenant/file identity, length and digest. For streaming, authenticate chunk position and the final manifest to detect reordering or truncation. Verify the image digest before provider dispatch. Limit plaintext metadata to lookup/retention fields. Protect sensitive names and source locators. Restrict paths to opaque IDs below the configured workspace and publish a complete file atomically. Key loss, authentication failure or reference mismatch blocks the read. Key rotation must retain old-version read capability until migration is verified. This adds a binary envelope to Files. The current local KeyVault service encrypts strings and already provides a trusted record API. ## Retention policy and transitions

The proposed host setting can coexist with the current temporary-upload settings.

```json
{
  "Retention": { "OperationalDays": 30 },
  "Files": { "DefaultTtlHours": 12, "PurgeIntervalSeconds": 60 }
}
```

Accept a positive whole number of days that can be safely added to the UTC clock. Reject invalid values at startup. Only a trusted operator sets the default. At creation capture `policyVersion=1`, `resumeWindow` and `terminalWindow` as the actual durations for this owner, initially both derived from `OperationalDays`. Changing the global default affects new owners. Support explicit user-kept outputs and reconciliation holds independently. Defer per-workflow duration overrides until a concrete use case requires them.

Persist in encrypted owner state the captured policy, lifecycle phase, revision, last meaningful checkpoint, wait entry, certain termination, computed deadline, expiry reason/time and purge progress as applicable. Exclude retention metadata from the approved workflow hash and historical wire identities. EF projects tenant, kind/ID, revision, lifecycle and due ticks for bounded scans. Use injected `TimeProvider.GetUtcNow()`. An owner is due at **now ≥ deadline**. Persist the deadline once per qualifying transition. A repeated delivery of the same transition preserves its anchor.

| Owner condition | Durable anchor and deadline | Ordinary behavior |
| --- | --- | --- |
| Planning generation, save in progress or executing run, live exclusive owner | Record semantic checkpoint time/revision. No running-owner expiry. A lengthy active call can exceed 30 days. | All purge attempts defer to the lease and in-flight operations. Cancellation requested alone does not prove termination. |
| Waiting for a person or explicit recovery action | Entry into this specific question/review or recovery wait + captured resume window. Persist the wait/invocation identity. Format 11 already has `WaitingSinceUtc`. Verify its relationship to the current wait. | Allow existing response/resume before deadline under the normal lease. A new legitimate wait gets a new entry. Human-response SLA/timeouts remain independently enforced. |
| Process interruption, no live holder | Last **published semantic** checkpoint + resume window. Capture creation time as the initial checkpoint. On restart under the lease, establish prior activity and recoverability from the journal. | Resume from the exact checkpoint within the window. Lost ownership proves neither provider failure nor external-effect certainty. Classify ambiguity before allowing a retry. |
| Certain terminal outcome | First durable completion, certain failure, certain cancellation, or completed save + terminal window. In format 11 an approved plan awaiting an explicit save can still need its dependencies. Treat it as a pending handoff until save/discard. | Inspection and delivery continue under existing permissions. A redundant terminal write preserves the original deadline. |
| `needs_reconciliation`, stopped planning with missing receipt, or uncertain external effect | First recorded unresolved transition + resume window for **ordinary** availability. Keep a separate evidence hold as soon as the ambiguity is known. | Only existing authorized reconciliation is available. When ordinary retention expires, restricted reconciliation can still retrieve indispensable evidence. A verified settlement can close its own hold. |
| Logically expired, purging, purged | Fence at the expected revision. Persist time, reason and original deadline once. | Ordinary resume, form commands and normal recovery return a typed `owner_expired` result. Preserve the ID and terminal fence. Creating a new owner requires a new explicit action and ID. |

Polls, downloads, technical indexing, lease heartbeat, purge retry and audit reads never advance semantic time. An explicit resume at the deadline must observe expiration even if the periodic worker has yet to run. In-flight work that won the lease and passed admission before the deadline remains protected. Do not infer idle or crashed status from `UpdatedAt`, file age or the mere existence of a lock file.

**Example in UTC.** A file uploaded April 1 at 08:00 gets a temporary deadline of 20:00. At 09:00 a planning session claims it. At 10:00 the plan enters review, due May 1 at 10:00 under its captured 30 days. On April 20 the reviewer approves and saves the version. A new run claims the image from the saved version and suspends April 21 at 12:00, due May 21 at 12:00. An inspection on May 20 changes neither deadline. At the May 21 boundary, a resume is refused even if collection has not run. The saved version's hold still protects the bytes. A new global seven-day default on May 1 applies only to owners created under that default.

## Publication, expiry and collection

Expose a protected operator preview such as `InspectRetention(tenantScope, asOfUtc, cursor, limit)`. A preview entry for a due run might report 900 KiB of distinct reachable bytes, 200 KiB pinned by a saved version, 100 KiB by an unresolved receipt and 600 KiB exclusively reclaimable. These are illustrative disjoint counts. The proposed apply operation takes the owner ID, expected revision and preview generation, rechecks eligibility using the current server clock and writes an audit receipt. A future preview date gives no early deletion authority.

1. **Establish a committed root.** For execution, put lifecycle data in the encrypted schema-9 document or the serialized header of the split head. Keep the existing blocks-before-head ordering. For planning, introduce one encrypted owner head pointing to the winning immutable revision, with owner identity, lifecycle, revision and payload key. Under the session lease publish the immutable payload first, then advance the head using the expected revision, then update the EF pointer. Make readers and recovery use that head. A crash before head publication leaves a candidate payload. A crash afterwards leaves a repairable EF projection. A same-revision competitor cannot select a winner by timestamp. Fence old writer processes before enabling this protocol.
2. **Publish a file dependency before its consumer.** Record an encrypted transfer intent on the destination owner or in its owner-scoped journal, including operation ID, expected revision and source grant. Under a Files transaction claim the blob and acquire a provisional hold. Verify the immutable bytes and commit the destination root with its file reference, then finalize the hold. For a transfer from a plan/saved version, keep the source hold until the destination root is durable. Recovery completes a referenced intent or releases an unreferenced provisional hold after proving the writer is gone. Do not infer abandonment from age alone. Acquire any multi-owner leases in deterministic tenant/kind/ID order. Files transactions never wait for owner leases.
3. **Inspect first.** A tenant-scoped read-only preview scans bounded EF pages, reloads trusted heads and reports expected revisions, anchor/deadline, owned object counts, logical bytes, exclusive reclaimable bytes, shared/protected bytes, oldest pending write and concrete reasons (`active_owner`, `saved_version`, `uncertain_call`, `unreadable_root`). Report unknown volume as unknown. Sum each physical blob/hash once within its storage scope. No state change, lease extension, model call or decrypted content in the report. Re-evaluate all fields at apply time.
4. **Expire logically.** Acquire the same exclusive owner lease used for resume and the normal short write lock where applicable. Under it reread the authoritative revision, deadline, effect/financial obligations, file operations and in-flight commands. If the revision changed, defer and rescan. Route every entry point, including automated queue recovery, cancellation, prompt replies, planning save and offline recovery, through the fence. Publish an encrypted owner tombstone with the revision, policy, cutoff, evidence pins and a purge manifest before releasing any dependencies. If resume wins, purge observes a live lease/new state. If expiry wins, resume observes the tombstone. Both paths retain the original execution ID.
5. **Purge physically in restartable batches.** Keep the fenced root and manifest until the sweep has enumerated the exact owned revisions, block prefix, file holds and protected evidence. Verify owner, current revision and purge generation at every restart. Trace all retained roots transitively, including before/after snapshots, header, events, retained historical roots and any quarantined effect evidence. For version 1, skip normal block collection for a live owner entirely. At expired-owner collection, keep the union reachable from protected roots or copy the exact needed payloads into verified evidence custody first. A seven-month-old block reached by yesterday's checkpoint survives. The schema-9 monolith is one unit. Use the optional KeyVault metadata cursor and targeted reads for bounded enumeration. If scope, graph or authority cannot be verified, retain and report.
6. **Finish file and index cleanup.** Atomically remove one recorded owner hold at a time. In Files, transition a blob with zero current grants, holds, pending attaches or active readers to deleting under a revision check. Concurrent attach before that transition preserves the file. Attach afterwards must fail or republish verified content under a new ID. Complete unlink, then delete metadata/retire key material after verified success. An unlink failure leaves a retryable row. A crash after unlink treats a proven absent blob as success for that deleting generation. Existing short downloads keep a read lease until their stream closes. Complete the encrypted purge checkpoint last. Keep a small permanent tenant/owner tombstone. Check it on create as well as read/resume, including the expected-null planning save path. Index rebuild reads tombstones and committed heads before projecting rows. It cannot choose an older payload or recreate a purged owner.

Use the same pending-write inventory for files staged before their references or blocks written before an interrupted root publication. Reclaim a staging generation only after the writer lease has gone, all relevant committed roots and intents have been checked, and the orphan grace has elapsed. A suggested 24-hour grace only schedules a check. Leave corrupt, unclassifiable or pre-migration objects quarantined for inspection. Restore backups with heads, tombstones, Files holds and evidence records from a consistent generation. If their generations disagree, disable resume and collection until verified.

### Independent evidence retention

Before deleting operational payloads, persist a minimal encrypted record keyed by tenant, original owner, invocation/request and physical attempt. Include artifact/approval hash and scope, request/body and available response/receipt digests, provider/effect correlation ID, observed status/phase, replay prohibition or explicit closure, timestamps, captured tariff/FX and usage, separate reserved/settled amounts, external effect disposition and reconciliation links. Protect sensitive locators through the same local KeyVault boundary. An exact pending provider body, response or external receipt needed by a supported recovery procedure remains pinned in full. A hash is sufficient only when the procedure no longer needs the bytes.

Keep unresolved records and reservations until authorized resolution, however long the operational TTL. For the first version, retain settled minimal financial/effect records and tombstones for the life of the ledger/owner namespace. Large captured bodies can be released once all exact-recovery, approval and independent audit dependencies are discharged. Any future financial archival policy requires a separate operator decision, preserved aggregates and durable no-replay identities. Campaign closures, settlements and user-kept output grants have independent authority. Purge may neither synthesize a closure nor settle a charge. Verify the financial audit and effect/replay disposition before and after physical cleanup.

## Validation gates

Use an injected clock and disposable workspace. Run against real Files/KeyVault/SQLite and reopen in a separate process for recovery and race cases. Assert exact IDs, revisions, file contents and financial records. Simulated timestamps belong only to the disposable fixture.

**Baseline verification for this proposal.** On Windows x64 and .NET 11, the existing Files.Server suite passed 10/10 and Flow.Persistence passed 28/28 in Release with warnings treated as errors. The clean test checkout was `4160c8ec`. Compared with the audited PR head, the only difference under `src` and `tests` was benchmark documentation. These results exercise the current storage behavior. The cases below are acceptance criteria for the proposed implementation.

| Fixture | Required observation |
| --- | --- |
| Restart just before expiry, then at the exact deadline | Same checkpoint and captured policy resume before the boundary. At equality the ordinary path returns `owner_expired`. A new ID appears only on explicit creation. |
| Human wait lasts longer than upload TTL | Staging access expires. The plan or run still resolves its claimed file. A download, poll, inspector read or failed response changes no deadline. |
| Active owner exceeds 30 days and then crashes | A second process cannot expire the live lease. After process exit the last committed semantic checkpoint supplies the anchor. No provider attempt is replayed. |
| Old block reused by a recent snapshot | Verify identical before/after data from the reopened run after an orphan sweep. Unpublished sibling block is reclaimable only after the writer check and grace. |
| Two valid owners and a saved deliverable | Expire each independently. Final release of the last hold makes bytes collectible. Cross-tenant ID, forged owner/header and known SHA fail. Revocation prevents fallback. |
| Resume/expiry barrier and crash injection | Force both winners with process barriers. Kill after upload, provisional hold, root commit, tombstone, unlink and before EF update. Restart twice. One legal state survives each time with no dangling live reference or double release. |
| Delete/rebuild scratch EF indexes | Recover identical lifecycle, selected planning revision and deadlines from committed roots. A surviving old payload cannot repopulate an expired owner. Pre-bootstrap ambiguity remains quarantined. |
