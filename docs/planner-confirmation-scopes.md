# Scoped confirmation policies

Schema-5 permission rules identify their governed action. Requiring confirmation
before external writes is compatible with prohibiting an unrelated human interaction,
including reviewing the workflow's YAML during execution.

The coordinator assigns source authority from owned source metadata. User requests
and answers can introduce requested actions. Existing actions require an issued node
reference into the current baseline. Host policies supply constraints only: their
response schema excludes operations, workflow creation and input/output declarations.
A policy mention of an effect is a scope, never a requested business operation.
Admission validates authority, semantic role, complete-clause evidence and the baseline
reference before obligations reach inventory, dependency or policy-target construction.
Restored candidates pass the same checks.

Preparation groups preliminary classifications by complete containing clause. One
bounded `confirmation_scope` decision adjudicates the entire group; initial labels
do not fix the resulting polarity. It distinguishes requiring permission, explicitly
forbidding a confirmation request, forbidding a particular interaction, and describing
rejection. A rejection condition references an issued required-permission rule, whose
locked rejection/unavailable branch already prevents the action. It cannot become a
confirmation prohibition. Equivalent requirements normalize only when their complete
clause, targets, applicability and permission semantics agree. Split-clause rejection
references retain both clauses.

Either preliminary confirmation label may become `not_confirmation_policy`. This
retires the classification's permission authority while retaining its complete source
as a workflow constraint. The original classification and page receipts remain audit
evidence. Unknown scope or unsupported adjudication stops technically. No wording,
provider, tool or benchmark-specific inference participates in these rules.

The pages retain routine reasoning, request ceilings, reservations and receipts.
Responses cannot introduce operations, executor-wide denials, arbitrary coordinates,
model-owned rejection actions or copied evidence. Known incompatible rule/scope
combinations fail the response schema.

`PlanningScopedPolicy` retains the governing obligation, clause reference, evidence
fingerprint, origin, applicability, target operation IDs and locked permission source.
It also retains every contributing obligation and evidence reference; obligations
retain source-grounding and adjudication fingerprints and their resulting disposition.
Effect classes expand against known operation kinds. An unrelated interaction
prohibition remains a workflow constraint; it does not deny the shared `human.input`
executor or authorize creation of that interaction. Other exact capability denials
retain their existing contract-validation path.

Required and forbidden confirmation conflict only when both apply to the same
canonical action. A declared `unless_explicit` default yields to an applicable explicit
intent/answer for that action; mandatory rules remain binding. Diagnostics include the
target and both governing references. Unknown scope or applicability stops technically
without asking the user to resolve an implementation question.

An ungoverned external write retains the platform confirmation default. A scoped rule
may also require permission for another declared action. Preparation introduces a
permission source when needed, or reuses the human decision already assigned to every
protected action. Sharing an executor, description or catalog entry is insufficient
to merge independent human interactions.

The coordinator constructs permission guards before executable topology is frozen.
Existing locked decision contracts bind the exact human response; only accepted
permission enters the protected branch. Business-result decisions keep their separate
outcomes. Behavior and executable validation reject missing guards, changed selectors,
prohibited interactions, and effects moved into defaults, parallel branches, loops or
finalizers outside their permission scope. Ordinary finalizers remain executable on
success, rejection and failure.

Scoped rules participate in preparation fingerprints and source-generated encrypted
serialization. Schema version and namespaces remain 5. Historical inventory snapshots
cannot establish scope proof; current decisions rebuild the inventory without
redispatching completed pages. Historical prepared contracts must be reassessed
through explicit revision before construction or approval. No archived campaign is
automatically resumed and cumulative budgets are preserved.

Internal preparation proof version **2** includes current source-grounding and
adjudication evidence in preparation fingerprints. Storage schema/namespaces remain
**5**; this is not a storage upgrade or decoder. Version-1 preparations cannot grant
authority without explicit reassessment. Redacted events identify authority rejection,
classification retirement and policy normalization; replay does not repeat successful
adjudication accounting.
