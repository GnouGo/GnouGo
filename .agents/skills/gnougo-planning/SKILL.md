# Planning

Preserve this architecture:

```text
User request
→ existing planning loop:
    accepted requirements + clarification when necessary
    ↔ bounded MCP discovery and exact-contract inspection
    → LLM business TaskPlan with selected operations
→ deterministic compiler → PlanningGraph → YAML
→ artifact review and approval → execution
```

Requirements, clarification and tool selection are responsibilities inside one bounded loop, not mandatory separate model calls. Clear requests with available contracts can generate a TaskPlan immediately. Accepted requirements remain the review baseline; resolved contracts determine which operations and data bindings are allowed. The removed model-authored technical outcome-proof layer does not return. Compilation validates executable contracts, not arbitrary prose completeness or execution success. Fresh intent version 3 may capture non-executable commitments: exact inspected operations and optional exact producer-port/public-output obligations. Assess those clauses deterministically after compilation; never infer commitments from the generated plan. Absent commitments, ambiguous occurrences and unsupported lineage remain explicitly unverified.

## Business intent and data

- The model selects business operations, inputs, results, dependencies and meaningful conditions. It does not author scripts, executor envelopes, wire paths or technical proof mappings. Add no planning phase, IR or integration-specific planner rules.
- No mapping executor in TaskPlan: **typed → JavaScript compiled at final lowering; insufficiently typed → DynamicMappingExecutor at runtime**. Use typed consumer bindings for copies and assembly; `extract` for observed JSON, text or HTML; reserve `interpret` for decisions, comparisons and synthesis. Omitted transform mode retains historical interpretation.
- Fresh extraction bindings infer independent collection processing only for an unambiguous source/target pair. Use existing `each: { input, output }` to select explicitly when needed: `input` exactly names a bound collection input, not the runtime item alias. `resultType` describes the complete assembled output: one candidate array per page requires `rows: array<array<Candidate>>`; scalar-per-item extraction needs no extra array. Exactly one result per item, same order, duplicates and nesting. No implicit filtering, flattening, ranking or aggregation.
- Bounded complete examples can generate a mapping; the script must process and validate every original item. Runtime independent extraction exposes canonical `item` and approved shared `context`; technical input paths do not belong in TaskPlan. Fresh adaptive bindings try a generic mapping, then specialize only unresolved shape/cause groups under the existing explicit cumulative runtime budget. All items still execute and validate; no partial publication. Representative complete examples are optional beyond one fitting initial item; specialization must include the actual failing item. Historical bindings retain one generation and one repair. Cache only validated source-grounded mappings per tenant. Missing required observations return `CONTRACT_UNSATISFIED`, never invented business values.
- Give each consumer its own closed extraction `resultType` and explicit selected input fields. Emit only observed facts needed for that decision; keep full observations and exact later action references separately. Optional candidates are an array per complete source item, empty only after checked absence. Explicit `flatten` with one operand concatenates one typed, nonnullable array-of-arrays level; it preserves ordering, duplicates, nullable elements and deeper nesting. No implicit flatten/filter/grouping. Global interpretation receives only the selected view and explicit shared context, never the raw snapshot alongside it and never sampled/truncated. Validate contracts, closed assembled inputs and the complete serialized request size; do not infer relevance or completeness from shape. Original producer metadata still establishes completeness. Oversized necessary views fail before dispatch.
- For selection, extract only identity plus the decision fields declared by `resultType`; the compiler never chooses relevance. Keep authoritative action arguments separately. Copy opaque identifiers and action references verbatim (`key: record.reference`); never shorten prefixes or decode identity components. Compact decision fields only; requested verbatim facts remain unchanged. Prefer producer IDs, otherwise attach original collection indices before extraction; no content hashes or renumbering. Interpret selects IDs; `lookup(port: key, items: [records, ids])` reconnects offered candidates, then original records. Repeated selections preserve order and repeat records; unknown or ambiguous source IDs fail atomically. Lookup is reconnection only, not a join/filter framework or learned mapping helper. Producer action checks still apply.
- Runtime mapping owns program/signature validation, global program repair and specialization of genuinely different data. Validate every original item and the exact target before publication; expose cumulative sandbox resources separately without raising limits. Keep business selection and external actions outside mapping.
- Ground extraction in observed properties and declared contracts; locator strings do not prove DOM ancestry, and unfamiliar URLs do not disqualify observed targets. Keep explicitly justified text/URL extraction available. Regex helper strings must preserve their intended backslashes through JavaScript and JSON; discarded escapes are global program failures, never shape failures. All-empty independent array results produce bounded count-only diagnostics, not automatic retries or proof of absence. Existing contracts and independent oracles decide acceptance. Never substitute blank/placeholder identities for unavailable selections.
- Use deterministic projections for known typed fields and original collection indices. For learned extraction, retain complete bounded producer collections and flatten declared results explicitly afterward. A declared `maxItems` does not override the host's effective collection limit. Never silently split work to reset inference or sandbox budgets; oversized inputs need an explicit compatible composition or a truthful limitation.
- Generate business actions, decisions, inference and effectful loops. Put copies, field selection, assembly, `flatten` and `lookup` directly in consumer bindings or scope outputs; do not name every intermediate as a task. Keep a necessary independent validation, shared computation or preservation boundary; document its purpose instead of removing it to meet a task-count target. Do not replace typed copying with inference or chain transforms merely to reshape the same data.
- Use one complete composition rather than a chain of adapter tasks: assert producer-declared success/availability/completeness → bind `pages` → `extract.each {input: pages, output: candidates}` producing `array<array<Candidate>>` → flatten into a compact decision → unchanged IDs → offered lookup in the consumer’s ordered `requires` → original-record lookup → requested actions → typed row exports and header assembly. Keep original observations separately. Empty inner arrays preserve examined pages. The fresh request includes the complete worked sequence and its exact `each` declaration; see the [complete example](../../../src/GnOuGo.Flow.Planning/README.md#independent-extraction-declarations-and-producer-repairs). Capabilities do not justify additional work; names or declared success flags do not establish a producer guarantee.
- Retain one minimal pure `foreach` only when existing bindings cannot express a necessary typed collection projection, such as selecting original record arrays or IDs from lookup results. Group related exports; use `field(item, property)`, never `field(array, property)`. `lookup` returns a record array even for one ID. Guard nullable IDs before lookup; project original text in the non-null branch and export permitted nulls in the other branch, with matching typed outputs. Validate selections against offered candidates before reconnecting originals. Never add learned copying, fabricated indices or a new operator to avoid this exception.
- Already typed collected records and structured cell rows use direct bindings and scope outputs, not another extraction, interpretation or forwarding `value` task. Retain a bounded projection when it provides a necessary collection check that flattening cannot prove. Preserve accepted output types, requiredness, bounds and nullability through revisions: a non-null record with nullable fields is distinct from a nullable record. Structural revisions do not authorize changing the accepted business interface.
- Return executable business tasks; GnOuGo compiles and saves their YAML. Use typed runtime bindings such as `{"kind":"input","source":"name"}`, never `${name}` inside a TaskPlan literal. External work uses discovered operations: extraction reads supplied observations, interpretation makes decisions or synthesizes requested content, and neither performs tool calls. Discover unavailable contracts rather than simulating operations. Create code or another workflow only when that artifact is a requested deliverable; do not replace requested execution with generating its instructions. Add no unrequested goals, side effects, filtering or deduplication. `choice` names a declared business choice, never an operation. Read operation results through typed `output` bindings; `present` establishes completion, not success. Extract facts only; assemble acquisition status deterministically from producer-declared results and snapshot metadata after checking the required preconditions. Mapping control predicates do not become observed result facts, and unrelated observed values are not status placeholders.
- When reporting exact facts, select one complete observed block, never synthesize several blocks. A requested description can be a complete features, characteristics or descriptive-text block without a Description heading. Several suitable blocks do not establish absence: select one relevant offered ID and reconnect its original complete text. Keep permitted null when no relevant block is observable or its association with the current subject is uncertain. Never join, paraphrase or shorten blocks; interface controls are not descriptions and do not establish business failures. Prefer producer-supported structured document rows over LLM formatting. Prepend supplied headers with `flatten([[headerRow], productRows])`; the extra nesting preserves the header as a row. Preserve whitespace, null cells and row order; inspect actual workbook content because schema compatibility alone cannot detect an omitted header.
- Defaults require authoritative declarations or accepted public-input defaults; absence differs from explicit null. Never create caller inputs to hide missing producer data.
- Extraction may return literal null for an unavailable fact only at an explicitly nullable target path. Every non-null scalar still needs an observed origin; never fill a missing fact with an unrelated observed value. Missing properties and defaults keep their existing semantics. Nullability does not prove that extraction preserved all relevant facts; retain independent execution oracles.
- Never generate a numeric executor. Ordinary formulas compile to JavaScript Number expressions; exact business arithmetic belongs to the owning MCP. Validate declared decimal conversions automatically at MCP boundaries.

## Contracts, scopes and compilation

- MCP producers own argument/result schemas, capabilities, effects, permissions and artifact provenance. Preserve opaque results; matching names or examples do not establish typed fields or resource ownership. No tool-name, provider-name or site-specific planner rules.
- When a producer offers observed action references, select from those candidates and let that producer resolve identity and validate action compatibility. Keep declared action intent explicit. Never synthesize references or treat labels as proof of control semantics; matching an action type does not prove the business decision was correct.
- Validate contract closure before final lowering: types, constraints, nullability, availability and authoritative provenance. Known incompatible values cannot escape through dynamic mapping. Compiler plumbing failures are compiler failures, not model repair requests.
- Validate schema alternatives against the complete supplied value, retaining sibling assertions and local references. Never pick the first object branch or combine fields from incompatible branches. Unknown expression values establish compatibility only; resolved runtime validation still enforces exact `oneOf` membership. A validator defect requires a validator fix, not a reordered producer contract.
- Keep normal exports in the normal execution path after their producers. Direct validated references stay direct; fuse compatible checked properties without losing intermediate constraints or observable identities. Reserve `finally` for genuine preservation/cleanup and exports that depend on its results; never spend cleanup capacity transporting normal outputs.
- Keep generated JavaScript readable by a human. Fresh `compact-bindings-v15` uses functional names, native projections and scope-aware checked lexical simplification. Reuse repeated reads and identity projections only within pure regions with unobservable reference identity; keep every ordered alias check and computed assertion at its original position. Retain coupled collection and capture contracts. Collect branch contracts before removing wrappers or aliases; retain each ordered check and keep genuinely conditional blocks. Eliminate technical branch envelopes only when selected required outputs prove equivalence; whole-result, coupled-schema and identity observers keep their containers. Keep schemas, ordered aliases and original origins in `expression_contracts`; controls use `control_contracts`. Only reached checks execute, before dependent effects. Strict lookup, first-present null behavior, exact JSON values and effective sandbox ceilings remain mandatory. Inline deterministic preparation into consumers; inference, budgets and receipts remain separate. Outputs execute after finalization: move terminal checks only when their timing, observers and enclosing durability are equivalent. Uncommitted pure work may be recomputed; committed inputs, decisions and results are reused without replaying effects. A technical receipt alone is not a reason to keep a set. Retain shared computation, pre-effect validation and observable control/recovery boundaries, and explain each retained set. Existing spans report reference-only outcomes, never observations. Preserve omitted/v1–v14 lowering and approvals; the model supplies typed bindings, never scripts. See [compact compilation](../../../docs/compact-workflow-bindings.md).
- `field` selects one declared object property, never an array index or length. Use existing iteration, flatten or lookup bindings for collections, or declare a required scalar result. Array `minItems`/`maxItems` are real cardinality contracts; a loop ceiling, boolean claim or objective text cannot substitute for them. Bounds do not increase host limits.
- Step `description` is optional literal observability metadata: business objective for business steps, concise deterministic purpose for technical steps. Keep `InternalRole` machine-readable. Never interpret descriptions or use them for execution, inference, permissions, validation or reconciliation; changing YAML metadata still invalidates artifact approval.
- `dependsOn` uses eligible same-scope identities; data references already imply dependencies. Capture ancestors, export descendant values through each scope, and reference the enclosing task's port. Conditional branches explicitly project the same consumer-facing ports with matching types, nullability and requiredness from their own observed values. Prefer direct typed ports over forwarding differently shaped whole results; valid object exports and opaque pass-through remain supported. Keep nullable ports nullable and use explicit null predicates on the consuming execution path—a separate availability boolean does not establish non-nullability. Never invent branch values or flatten/cast opaque contracts. Interface restructuring outside issued repair slots requires explicit revision. `present(inner)` cannot reference an inaccessible descendant or be silently replaced with `present(container)`.
- Keep fixed agent scope and host-owned bindings immutable. Save available failure evidence inside the appropriate finalizer before nested cleanup. Unknown external completion blocks both cleanup and replay.
- `requires` is the local runtime assertion on the affected task, not a separate guard task: false fails before its work. `and`/`or` have two operands: nest three producer-declared checks as `success AND (available AND complete)`, protecting nullable access before completeness checks. These names are illustrative, never inferred flags. Keep each `field.port` an exact declared property; punctuation belongs to the name, not predicate syntax. Do not sanitize references. Preserve short-circuit order and effects; branches route optional work. The compiler checks types, scope and availability, not implication. Automatic repairs cannot change `requires`; an explicit targeted revision is required. Never infer permission from names or remove work to pass validation.
- Keep generation guidance cohesive and executable. Fresh full-proposal schema hints explain `requires` (failure, not skipping), conditional routing, transform modes, `each` and complete assembled `resultType`. They do not change acceptance, handwritten YAML or historical omitted-mode behavior. Preserve private repair templates, authority fingerprints and already-issued prompts/schemas; context guidance grants no new edit permission. Deterministic adapters prove expressibility and execution, not model compliance.
- Preserve declared constraints in authoritative validation. Project only provider-incompatible schema features out of a cloned model-facing schema before estimation, hashing and persistence. Preflight before dispatch; retain issued requests unchanged.

## Interaction, repair and approval

- Ask only material business ambiguities in the existing planning loop. Discovery may leave requirements null; clarification returns questions without a plan. The first TaskPlan must declare requirements and caller/output interfaces, and accepted requirements remain authoritative. Before any baseline is accepted, diagnosed invalid/missing requirements (including intent-version 3 commitment declarations) can use the policy-authorized single regeneration within the existing allowance; another invalid proposal stops. Never synthesize requirements from a rejected plan. Questions support recommended alternatives and custom text, pause automatic mode and grant no runtime permission. Fresh interaction policy 1 preserves accepted requirements, correction scope, history and cumulative attempts after answers. A clarification pauses the existing correction; it is not a failed candidate or permission for another structural fallback. Ask only when allowance remains to use the answer; exact repeated answered questions stop. Auto reuses accepted choices, never treats recommendations as authority. Requirement/interface changes need a separate explicit revision.
- Keep commitments separate from tasks: no task IDs, scheduling, predicates or proof mappings. For `{"operation":"<inspected ID>","result":{"port":"location","output":"filePath"}}`, `location` is a declared producer port and `filePath` the public-output name, never its path/value/description. `result: null` means operation-only, not a substitute for invalid metadata. Complete unresolved obligations during discovery and freeze them before accepting the first plan; correction cannot change them. Missing reachable operations and disconnected producer-owned outputs are violations; operation presence does not prove arguments, per-item work, relevance or runtime success. Confirmed violations block approval. Explicit human acknowledgment may accept unverified coverage but must leave it labeled unverified. Recompute coverage at approval; preserve historical intent/version hashes.
- Review accepted requirements beside actual operations, loop bodies and bindings. Artifact approval requires explicit `ReviewedRequirementIds`, current revision and artifact hash. Never populate acknowledgments automatically; compilation is not proof of business completeness.
- New hosts omit redundant startup confirmation; explicit policy opt-in, historical confirmation workflows, MCP permissions and business questions remain effective. Actions follow the user request and available contracts.
- Prefer targeted `revise` with `preserveRequirements: true`, current revision/hash and explicit `editablePaths` for bindings and an existing transform's `mode`, `each` or `resultType`. These semantic declarations require explicit revision, not automatic repair. Preserve unrelated operations, objectives, ordering, scopes and cleanup. Structural redesign requires an explicit global revision.
- A session-captured automatic-correction policy may authorize a new targeted implementation revision or one structural regeneration before approval. Reuse existing revision/repair paths and cumulative allowances; never broaden issued authority. Preserve requirements, public contracts, independent work, assertion ordering, operations and cleanup. Stop on unknown failures or changes whose preservation cannot be established. Post-execution correction creates a separate unapproved draft, never replay or modification of the approved workflow. Handwritten YAML without recoverable intent pauses for clarification.
- Intent-version 2 private correction version 3 may remove only an export diagnosed as unaccepted before issuing the correction. Accepted requirements, not an invalid proposal's extra exports, own the public interface. Preserve remaining names, order and independent bindings; changing an operation's instructions requires separate authority. Complete output validation still applies. Version 3 retains the version-2 diagnosed nullable-guard correction: `value != null`, optionally conjoined with nonnullable Boolean fields from the same producer, preserving the original reference and valid surrounding checks. Unknown types, invented success, new OR, completion substitution and unrelated edits remain blocked. Historical versions 1–2 and pending requests keep their original semantics. Passing preservation is not business acceptance; see the [correction rules](../../../src/GnOuGo.Flow.Planning/README.md#bounded-automatic-correction).
- Intent-version 3 private correction versions 4–5 may capture a narrowly permitted addition of an inspected operation already required by an accepted commitment. Fresh version 5 resolves a public-output diagnostic to its exact existing root export only when the accepted name is unambiguous; retain original diagnostics and literal names, and never widen to another output or ancestor. Ordinary patches gain no structural authority. Regeneration preserves existing effects/arguments/order, guards, finalizers, independent tasks and scope exports; only diagnosed exclusive pure adaptation may change. Reject duplicate/unrelated effects and unknown placement rather than guessing from types. Historical requests/progress keep their original authority and cumulative limits. Progressive construction needs retained evidence before adding complexity.
- Initial discovery under automatic correction reserves a proposal, one available repair and a clarification until answers are recorded. Releasing a reserve adds no allowance; repeated clarification may still exhaust it. Pending requests keep their original schema. `TASK_LITERAL_INVALID` may use an existing editable value slot, never protected assertions or host-owned arguments; do not strip/escape interpolation or invent success. Missing work or changed accepted outcomes needs explicit revision.
- Repairs use only diagnostic-derived typed slots, applied atomically to a clone and fully revalidated. New envelope-10 slots share generation’s existing `flatten`/`lookup` vocabulary; `json` encodes text, never binding instructions. Test the actual emitted request, including recovery, rather than a separately constructed schema. Broken producer references may select compatible ports or authorized export chains, never replacement literals. Require explicit revision when immutable guards or missing producers cannot be repaired within issued authority.
- Diagnose extraction at its producer: check bound input names, `each` and the assembled `resultType` before changing a consumer. Invalid declarations or immutable `requires` stop with `REVISION_REQUIRED` when issued edits cannot resolve them, including mixed consumer errors. Use explicit targeted revision for the responsible declaration/guard. Read-only producer bindings explain the source without granting edits. Apply already-issued receipts before fresh-request checks; do not replace their schemas or redispatch them.
- Preserve issued repair envelopes, receipts, cumulative budgets, historical approvals and tenant ownership. Revisions invalidate current artifacts/approval. Designer advancement needs the existing cross-process lease; unknown completion remains stopped, never a free retry.

## Validation and references

Reproduce failures deterministically with independent execution oracles. Check exact output values, effects, cleanup and recovery—not compilation alone. Preserve all failed evidence. Paid evaluations require authorization, fresh identities, frozen cohorts and shared cumulative accounting; never replay uncertain invocations.
